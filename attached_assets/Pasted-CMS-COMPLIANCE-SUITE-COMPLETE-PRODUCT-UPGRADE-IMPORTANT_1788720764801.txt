CMS COMPLIANCE SUITE — COMPLETE PRODUCT UPGRADE

IMPORTANT

You are modifying an existing web application.

Do NOT rebuild the application from scratch unless technically necessary.

First inspect the entire existing application, its current architecture, components, data structures, navigation, styling, functionality, and responsive behavior.

Preserve existing working functionality unless these instructions explicitly replace or improve it.

The goal is to evolve the existing product into a more comprehensive professional CMS compliance platform.

2. POSITIONING

The application should no longer feel like a simple CMS policy/template tool.

Position it as a:

CMS compliance, policy management, gap assessment, and survey-readiness platform.

The core workflow should communicate:

Select Provider Type → Identify CMS Requirement → Assess Compliance → Build/Review Policy → Identify Evidence → Prepare for Survey → Track Corrective Action

The application should support both:

Conditions of Participation (CoPs)
Conditions for Coverage (CfCs)
Do not imply that every provider type uses CoPs. Use the correct regulatory terminology based on the provider type.

The interface should feel like one integrated compliance platform, not seven unrelated tools.

17. CMS / CFR SOURCING

This is extremely important.

Do not invent CMS regulations, CFR citations, or official CMS requirements.

Where a requirement is represented as an official regulatory requirement, provide:

CMS reference
CFR reference where applicable
Source designation
Last reviewed/verified date where appropriate
Clearly distinguish between:

Official Requirement

and

Application Guidance

and

Suggested Best Practice

The product should never imply that AI-generated guidance itself is an official CMS requirement.

Provide a way for the underlying CMS requirement library to be updated as regulations change.



18. “LAST VERIFIED” FUNCTIONALITY

Add the ability for CMS requirements to have:

Last Verified

and, where useful:

Next Review

This is particularly important because CMS requirements can change.

Do not claim a requirement is current unless the underlying source has actually been verified.

22. MULTI-PROVIDER SUPPORT

Design the architecture so a consultant or health system can eventually manage multiple organizations/providers.

The application should not hard-code a single provider into the entire application.

Structure the data model so it can support:

Organization → Facility → Provider Type → Requirements → Policies → Gaps → Corrective Actions

This is particularly important for future expansion into healthcare consulting.

Do not necessarily build a complex multi-tenant system unless the existing application already supports it, but make the architecture extensible.
